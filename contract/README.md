# The estate report contract

`clearcutt-verify` writes what it found and proved about an image estate as
an **estate report**. Anything can read it, including
[clearcutt-portal](https://github.com/northcutted/clearcutt-portal), which
turns it into a website. Readers never need registry access, a ClearCutt
binary, or this repository's code: the report and these schemas are the whole
interface.

| File | What it is |
|---|---|
| [`estate-report.v1.schema.json`](estate-report.v1.schema.json) | JSON Schema (2020-12) for `kind: EstateReport`: one verification run |
| [`estate-history.v1.schema.json`](estate-history.v1.schema.json) | JSON Schema for `kind: EstateHistory`: past runs' headline numbers, newest first |
| [`trust-policy.v1.schema.json`](trust-policy.v1.schema.json) | JSON Schema for `kind: TrustPolicy`: whose signatures an organization accepts, for images (role `image`), clearcutt-factory stacks (`stack`), and the estate's own report bundles and history indexes (`estate`). clearcutt-verify (`estate verify --trust-policy`, or `trustPolicy:` in a VerificationPolicy; `estate pull`/`history --trust-policy`) and clearcutt-factory (`signing.trustPolicy`) read the same file; each field is described in the schema |
| [`examples/minimal/`](examples/minimal) | A small, synthetic bundle covering every status (images under `acme`, made-up digests), and a trust policy |
| [`fixtures/northcutted-images/`](fixtures/northcutted-images) | Generated by `clearcutt-verify estate verify` from a real estate: the clearcutt-factory example fleet `ghcr.io/northcutted/images` and its Chainguard and Docker Hub bases |

The schemas are generated from the Go types in
[`cli/internal/report`](../cli/internal/report), and descriptions in the schemas
come from those types' doc comments. A test fails when they drift, and every
document under `examples/` and `fixtures/` is validated against them.

## The bundle

A run writes a **bundle**: a directory with

- `estate-report.json` (required): the report.
- `estate-history.json` (optional): the history, when the run was given one.

A portal is pointed at a bundle directory. Planned: bundles will also be
stored as OCI artifacts in the registry next to the images, the way `estate
push` already stores estate snapshots, so a fleet's history travels with its
registry; exporting a stored bundle back to a directory gives the same files.

## Reading it

**Status vocabulary.** Every evidence item has a `status`, and the
difference between them is the point:

| Status | Meaning | Show it as |
|---|---|---|
| `verified` | Found, and checked against one of `policy.trustedSigners` | proven |
| `present` | Found, but not checked: no trusted signer applies, or it can't be checked | exists, unproven |
| `failed` | Found, and the check failed (wrong signer, bad signature, digest mismatch) | a problem |
| `missing` | Looked for, and there is none | absent |
| `unknown` | Couldn't be looked for or checked (registry error, unsupported store, cosign couldn't reach a registry or the transparency log, not every platform image could be read) | unknown, never as absent, zero, or a pass |
| `not-applicable` | Doesn't apply: a rebase record for an image that was never rebased, or the recipe of a rebased image whose rebase record is `verified` (a rebase record that is `present`, `failed`, or `unknown` never excuses a missing recipe) | omit or grey out |

What the report reads out of evidence (`vulnerabilities`, `packages`,
`source` with `basis: provenance`, `factory`) comes only from evidence that is
`verified`; nothing in `present` or `failed` evidence is read. A verified
item's `signer` is the signer cosign checked; on any other status it is what
the evidence's certificate claims, unverified. `signer.tlog: false` on
verified evidence means cosign checked the key's signature but no
transparency log entry, because the policy's key signer says it signs
without one. `source: github-attestation` marks a GitHub artifact attestation
in the registry (told by its verified content, so only on verified
evidence), and `signerWorkflow` names the GitHub Actions workflow that signed
verified evidence the way `gh attestation verify --signer-workflow` takes it
(`signer.sourceRepository` gives its `--repo`). A rebased image's `factory`
kind, name, and stack (`stack`, `stackRef`, `stackDigest`) come from the
verified recipe of the image it was rebased from, reached through verified
rebase records, so rebased apps are listed under `stacks` too.

**Platforms.** `metadata.platforms`, when present, lists the only platform
images the run read (`estate verify --platforms`): per-platform evidence
(SBOMs and vulnerability reports, `evidence.*.platforms`), findings, and
packages describe those platforms only. Absent, every platform image was
read.

**Bases.** `base.strength` says how an image's base is known: `proof` means the
image starts with the base's exact layer digests (`method: layer-prefix`);
`declared`, `assisted`, and `weak` rest on what the image's author wrote.
Never show a claim as proof. Images without `base` are either `root` (it
says why) or `unresolved` (it says why not). `base.daysBehindUnknown` marks a
stale base whose `daysBehind` couldn't be measured: unknown, not zero.

**Vulnerabilities.** An image without `vulnerabilities` has no vulnerability
data: unknown, not clean. `summary.vulnerabilities.notScanned` counts those.
Findings are read only from verified scans in grype's format, for now; an
image whose verified scan is another scanner's has none either, and its
`evidence.vulnerabilityScan.detail` says so.
`scannedAt` says what day the findings describe: the publisher's scan is as
old as the image, so what was published since is unknown.

**Rescans.** With `policy.rescan: true` the run scanned each image's
*verified* SBOMs itself (grype, `estate verify --rescan`), and
`images[].rescan` sits beside `vulnerabilities`: the publisher's scan and the
run's own, side by side. `rescan.status` is `scanned` (every platform image's
verified SBOM was scanned) or `unknown` (a platform image has no verified
SBOM, not every platform image could be read, or grype couldn't scan it:
`rescan.detail` says which, `rescan.platforms` which platforms). Only
`scanned` carries `rescan.vulnerabilities` (`source: scan`, with `scanner`,
`scannedAt`, and `database.built`, the vulnerability database's build time:
the scan knows nothing published after it). An `unknown` rescan means the
image's current vulnerabilities are unknown, never clean, and
`summary.rescan` counts `scanned` and `unknown` images and totals the
findings. `policy.scanSource` says which scan `policy.failOn` gated on:
`attestation` (the publisher's; the default without a rescan), `rescan`, or
`worst` (both; the default with a rescan). `policy.maxScanAgeDays` measures a
`scanned` rescan by `database.built`.

A finding either scan suppressed is listed with `suppressed: true` and is not
counted. In a rescan, `suppressedBy` names what suppressed it: `source: vex`
with the OpenVEX document the policy named (`file` as written in the policy,
`document` its `@id`), the statement's `product` as written, `status`, and
`justification`; or `source: scanner` for grype's own rules. A suppressed
finding without `suppressedBy` was suppressed by the publisher's scan with a
statement this run didn't see. `policy.vex` lists the documents applied.

**Observe-only images.** `images[].observeOnly: true` marks an image the policy
observes without gating on (`policy.observe` patterns): it has a `verdict`
like any other, but it is counted in `summary.verdicts.observeOnly` instead of
`verified`, `failed`, or `unverified`, and `estate verify --fail-on` ignores
it. `verified + failed + unverified + observeOnly` is `summary.images`.
Absent, the image gates.

**Provenance.** A `verified` `evidence.provenance` means cosign verified the
attestation's signature against a trusted signer and that the statement is
about the image, and the source repository and commit were read from it
(`source`, `basis: provenance`). It does not mean the builder, build type, or
materials were evaluated: `images[].provenance` shows the builder ID and build
type as read, and `builderChecked: true` only when `policy.provenanceBuilders`
named the builder (provenance naming another builder, or none, is then
`failed`, and neither `images[].provenance` nor `source` is read from it).

**Reproducibility.** `reproducibility.source` says how an image was found to
reproduce: `rebuild` (this run rebuilt it) or `attestation` (a
clearcutt-factory reproduction attestation on the image, verified against a
trusted signer and made from a recipe or rebase record verified on the same
image; this run didn't rebuild it). An attested result names who signed it
(`signer`), where it is stored (`ref`), and the run and machine that
reproduced it (`builder`, as the attestation says). Absent, nothing checked
it.

**Packages.** `packages` lists what the images whose package sets could be read
ship; `summary.packages.unknown` counts the rest. "No image ships X" is only
true when that count is zero.

**Verdicts.** `verdict.status` is `verified` (meets every requirement in
`policy`), `failed` (violates one), or `unverified` (a requirement couldn't be
decided). A `verified` verdict rests on at least one piece of the image's
evidence being `verified`, so with no `policy.trustedSigners` every verdict is
`unverified`. `verdict.reasons` lists one line per requirement not met.
`policy.maxDaysBehind` fails an image only on drift from a base proven by
layer digests; drift from a claimed base leaves it `unverified`.

The meaning of a verdict is part of the contract. clearcutt-verify v0.16.0
changed it under `clearcutt.dev/v1`: before, an image none of whose evidence
verified could be `verified` on checks that read no evidence; since, it is
`unverified`. That was a tightening (nothing that was `failed` or
`unverified` became `verified`), made without a `v2`, and it is the kind of
change the rules below say needs one. To keep it from happening unnoticed
again, clearcutt-verify's tests recompute every verdict in the bundles under
`examples/` and `fixtures/` from their recorded evidence and policy and fail
when one differs; changing what a verdict means now means changing those
bundles in the same change, with a CHANGELOG entry under "Breaking".

**History.** Each `estate-history.json` entry has the run's summary and a row
per image (`images`): its digest, verdict, base, rebase, and vulnerability
counts (and `rescanVulnerabilities`, the run's own scan's counts, when it
rescanned; `observeOnly` when the image didn't gate). To show what changed between runs, a row also lists
`fixableFindings`, the IDs of the image's fixable high and critical findings
(VEX-suppressed ones aside) from its verified scans, and `packagesDigest`,
which identifies its package set (sha256 of its sorted `type name
version\n` lines, as in the report's `packages`, from verified SBOMs). Other
findings are only counted, to keep the history small. A row with
`vulnerabilities` and no `fixableFindings` has none; without
`vulnerabilities` they are unknown, and without `packagesDigest` so is the
package set.

**Identity.** `images[].id` is unique in a report, one URL path segment
(letters, digits, `.`, `_`, `-`), and the same in every run for the same image
reference, so it works in URLs and joins runs in the history. clearcutt-verify
makes it from the whole reference: registry, repository path, and tag (or the
first 12 hex digits of a digest), lower-cased, every run of other characters
one dash, the tag `latest` left out (`ghcr.io/acme/billing:1.2` is
`ghcr-io-acme-billing-1-2`, `debian:trixie-slim` is
`docker-io-library-debian-trixie-slim`). Two references that spell the same ID
each get the first 8 hex digits of the sha256 of the reference appended, so an
ID never depends on the order images were listed in. Treat IDs as opaque:
match them, don't parse them. `base.imageId` links to the base when the base
is in the report.

## Versioning

`apiVersion: clearcutt.dev/v1` changes only additively: new optional fields,
new enum values in fields documented as open (`builder.kind`,
`evidence.*.source`). Readers should ignore fields they don't know and show
unknown enum values as-is. Anything else (removing or renaming a field,
changing a meaning) needs `v2`, with both versions written for a release
before `v1` is dropped.

The published schemas reject unknown fields (`additionalProperties: false`),
so they catch a producer that drifts from the types. clearcutt-verify checks
every report and history against them before writing it, and writes nothing
(exit 1) when one doesn't match. A reader that validates
reports against a copy of a schema should allow unknown fields when it does,
as clearcutt-portal does, or a newer report with an added field fails a check
it should pass.

## Changing it

The contract belongs to `clearcutt-verify`. To propose a change, open an issue
on [northcutted/clearcutt-verify](https://github.com/northcutted/clearcutt-verify/issues)
saying what a reader needs and why. Changes land as a change to the Go types,
the regenerated schemas (`go -C cli test ./internal/report -update`), and the
examples.
